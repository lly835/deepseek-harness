# Agent Note：自定义模型行可编辑思考档位

Status: implemented

[English](2026-08-14-custom-model-reasoning-efforts-ui.md) | 中文

## 问题

`llm-pi-ai` 后端已经允许每个配置模型声明 `reasoningEfforts`，Composer 也会根据适配器返回的精确模型能力渲染思考档位选择器。手工声明的模型没有已安装 catalog 条目可以继承这项能力，因此如果省略 `reasoningEfforts`，Harness 会把它视为没有可选推理档位，Composer 自然也不会显示思考强度控件。

模型设置页此前可以编辑 pi-ai 模型的 id、名称、上下文窗口和最大输出 token，却不能编辑推理声明。用户添加一个具备推理能力的新模型或 OpenAI-compatible 网关后的模型时，即使后端 schema 与分派路径早已支持该字段，也必须离开网页手工修改 `settings.yaml`。

把思考档位放在提供方级别并不能解决这个问题：同一提供方下的不同模型可能支持不同档位，也可能使用不同的协议值。能力声明应属于模型行本身。

## 决策

pi-ai 模型列表编辑器在每个模型行的“高级设置”中暴露 `reasoningEfforts`。可选档位沿用 pi-ai 的 provider-neutral 词汇并按强度顺序展示：`off`、`minimal`、`low`、`medium`、`high`、`xhigh`、`max`。

勾选一个非 `off` 档位时，会把它加入模型声明，并默认使用档位名本身作为实际发送的协议值；如果网关使用其他拼写，可以在旁边的协议值输入框中修改。只有至少存在一个真正的思考档位后才能勾选 `off`；`off` 的协议值允许留空，此时保存为 `null`，沿用适配器现有的“支持关闭，但不发送 effort 值”语义。删除最后一个非 `off` 档位时，会连同 `off` 一并移除整个声明，让模型恢复到继承/未声明状态，而不是留下后端会拒绝的仅 `off` 无效映射。

编辑器继续保留它不负责的模型字段。已有的 `reasoningEfforts: false` 和手写声明在用户没有操作推理控件时保持不变；一旦用户明确选择思考档位，非推理标记会被新的档位声明替代。非 `off` 档位不允许提交空协议值，因为适配器本身会拒绝这种配置。

本次修改不增加 GLM、DeepSeek 或 OpenAI 的硬编码行为，也不修改 `dsh-llm` 或 `llm-pi-ai` 的请求分派。真实端点支持哪些档位仍由用户声明。`compat.thinkingFormat` 等 provider/model compatibility 开关继续作为独立配置，因为它们描述的是“如何在协议中运输推理参数”，而不是“模型提供哪些档位”。

## 验证

新增一组聚焦的 jsdom 测试，直接渲染真实 `ModelListEditor`，固定以下行为：创建档位声明、保留无关模型字段、自定义协议值、`off` 的 nullable 值、拒绝提交空的非 `off` 协议值，以及删除最后一个思考档位后恢复继承。既有 `llm-pi-ai` catalog 测试继续负责 `reasoningEfforts` 的 schema 与分派验证。

## 备选方案

**增加一个提供方级思考强度下拉框。** 不采用。同一路由内的模型可能支持不同档位与 wire 映射，一个提供方级值可能只对部分模型有效。

**自动把所有自定义模型标记为支持推理。** 不采用。模型列表发现接口没有提供可移植的推理能力描述；猜测能力会让界面暴露实际端点无法接受的选项。

**硬编码 GLM 的思考档位。** 不采用。该页面配置任意 pi-ai 路由和网关，而且不同 GLM 部署也可能使用不同兼容层；现有的逐模型声明才是正确事实来源。

## 后果

手工声明的推理模型现在可以直接在模型设置页完成能力声明，随后现有 Composer 就能展示它配置过的思考档位。用户不再需要仅为了新增或改名模型级思考档位而手工编辑 `settings.yaml`。界面仍然是声明式配置：它不会探测或保证实际端点一定接受用户填写的档位与协议值。
